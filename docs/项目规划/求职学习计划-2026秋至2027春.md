# C++ / Qt 求职学习计划（2026 秋至 2027 春）

> 制定日期：2026-08-12。本文是当前求职导向的执行计划；技术进度仍以 `C++Qt学习路线-完善版.md` 为唯一真相。每完成一个有证据的阶段，同步更新路线、技能清单和两份主题笔记。

## 1. 个人定位与现实目标

### 本地学习档案

- 学历背景：双非本科；
- 经历基线：零实习；
- 当前优势：已有 Qt Widgets、TCP/HTTP、Asio Session、协议分帧、JWT/SQLite Auth 与 ChatHub W8 的连续项目证据；
- 当前短板：没有可公开、可复现的完整作品集；CMake/测试/数据库/调试还缺少独立迁移证据；算法、操作系统、Linux 与面试表达需要体系化补齐。

这份档案仅用于本地学习与求职规划。后续会话默认以此定位安排任务，除非用户主动更新。

### 目标不是“等准备好再投”

从现在起同时运行两条线：

```text
实习 / 秋招投递线：立即投递 → 面试暴露短板 → 定向补齐 → 继续投递
能力与作品线：完成企业级单机 ChatHub → 测试/文档/演示 → 转为简历证据
```

目标是争取一段与 C++、Qt、桌面客户端、工业软件、设备通信或通用应用开发相关的实习，并把实习中的真实模块、缺陷定位和协作流程沉淀为春招证据。实习结果无法保证，但计划不允许因等待实习而暂停投递或作品建设。

## 2. 岗位方向与取舍

### 主投方向（70%）

- C++ / Qt Windows 或跨平台桌面客户端；
- 工业软件、仪器仪表、自动化、仿真、设备管理、数据采集工具；
- C++ 应用软件、通信客户端、SDK 或客户端基础模块。

理由：这些岗位最能复用现有 Qt Widgets、网络协议、SQLite、错误处理和调试能力；对“能交付一个稳定模块”的要求，比追求分布式大项目更直接。

### 次投方向（20%）

- C++ 通用软件开发、网络通信、工具链或测试开发；
- 有 Qt、Windows、Linux、TCP/IP 或 SQLite 交集的实习。

### 探索方向（10%，只投匹配岗位）

- Linux C++ / 嵌入式应用层 / 串口上位机；
- 不把驱动、音视频编解码、高并发分布式、游戏引擎、算法岗作为当前主线。它们需要另一套深度，短期会稀释作品与面试准备。

## 3. 面对 AI 编码的能力标准

AI 可以用于查资料、生成候选方案、解释报错、补重复代码和设计测试，但简历上的每项能力必须通过“无提示复盘”验证：

1. 能画出数据流和生命周期，解释为什么这样划分职责；
2. 能在不复制答案的前提下修改一个需求或修复一个故障；
3. 能构造失败输入、写/补测试，并说明测试防住什么回归；
4. 能在面试中打开仓库，15 分钟讲清“问题—方案—取舍—验证”；
5. Git 提交、需求文档和缺陷复盘能证明过程，而非只有最终代码。

因此，目标不是“完全不用 AI”，而是达到 **AI 辅助下仍能审查、调试、验证与负责**。这正是零实习候选人可以展示的差异。

## 4. ChatHub 的完成深度：企业级单机全栈

ChatHub 的定位升级为“可部署、可测试、可解释的单机全栈即时通信系统”。企业级指的是清晰分层、数据一致性、安全边界、测试与交付能力；**不等于**伪造多机集群或堆无关功能。

```text
Qt Client
  ├─ HTTP → Auth Service（Node/Express、JWT、Redis 限流）
  └─ TCP  → ChatServer（C++17/Asio、协议、Session、路由）
                    └─ MessageRepository → SQLite（开发/测试）→ MySQL（集成交付）

Docker Compose：只编排 MySQL 与 Redis；Qt 客户端仍由本机 CMake 构建运行。
```

### 必须完成的六个阶段

| 阶段 | 必须交付 | 可验收证据 |
|---|---|---|
| W9：领域与 SQLite 持久化 | 稳定 `message_id`、消息状态模型、SQLite 表/索引/事务、最近历史、重连显式加载。 | 重启后历史正确；重复请求不重复写入；数据库失败有可见错误。 |
| W10：可靠性 | 认证超时、容量契约、幂等、待送达过期、结构化日志、关键路由自动化测试。 | 非法帧、断线、超长、重复回执、数据库不可用均有测试或可复现验收。 |
| W11：MySQL 集成 | 抽象 `MessageRepository`；保留 SQLite 测试实现，新增 MySQL 集成实现与迁移/初始化脚本。 | 同一业务测试可在 SQLite 与 MySQL 环境运行；查询走索引并能解释事务边界。 |
| W12：Redis 与安全 | Auth 服务用 Redis 做登录限流（必做）；在明确 `jti` 生命周期后实现 JWT 撤销检查（进阶）。 | 限流 TTL 正确、误输不影响正常账号；撤销 Token 后新认证被拒绝。 |
| W13：交付与验证 | Docker Compose、CMake Presets、CTest/集成测试、GitHub Actions、配置模板、README、架构图、压测与录屏。 | 新环境按文档启动依赖并跑通；3–20 模拟客户端回归；CI 自动构建/测试。 |
| W14：联系人与好友闭环 | 用户搜索、好友申请、接受/拒绝、联系人列表；仅允许已建立关系的双方新建私聊，并补关系表、权限校验和端到端测试。 | 非好友不能发起私聊；重复申请、交叉申请、拒绝、解除关系均有可解释结果；好友建立后可从联系人进入既有私聊。 |

> W14 以 llfcchat 的好友流程为蓝图，但只在 W13 工程交付验收后开始。完整参考规则见 [`llfcchat参考索引与对照规则.md`](./llfcchat参考索引与对照规则.md)。

### 明确不做

- 群聊、图片/文件、已读、多端同步、音视频、WebSocket、gRPC/Protobuf、消息队列、多 ChatServer、Redis Cluster、分布式锁；
- 客户端直连 MySQL 或 Redis；
- 没有明确业务理由的缓存、异步队列和微服务拆分；
- 把“数据库写成功”伪装成“跨设备可靠投递”。

### 关键工程边界

- `message_id` 是持久业务身份；`SessionId` 只代表瞬时连接，不能进入长期消息归属；
- SQLite 用于快速验证 SQL、测试隔离和本地开发；MySQL 是项目集成交付数据库，二者不能同时作为生产真相；
- Redis 不是聊天消息库。登录限流的计数器和 TTL 是第一处明确职责；JWT 撤销只在定义好 `jti` 与过期清理后接入；
- 先完成单 ChatServer 下正确的状态与测试，后续若研究 Redis 在线状态或多服务器，必须作为独立 spike；
- 每一项新技术先有最小实验、再有需求文档、再进入 ChatHub 主线。
- llfcchat 是局部代码对照库：先独立设计/尝试，再阅读一个函数附近的 10–30 行并记录差异；不复制其全局单例、工程结构或生成代码。

### 每周最低节奏（无实习时）

- 40%：可提交的项目/测试/文档；
- 25%：算法 + C++/网络/数据库/操作系统基础；
- 20%：投递、岗位拆解、简历迭代、模拟面试；
- 15%：英语技术文档、复盘、GitHub 整理。

拿到实习后改为：60% 把实习模块做深并记复盘，20% 算法与基础，10% 保持项目，10% 继续投递或准备春招；不能因实习停止面试准备。

| 模块 | 春招目标 | 证据标准 |

| Qt Widgets | 信号槽、事件循环、布局、Model/View、对象树达到“能设计”。 | 两个项目都能解释 UI 与数据模型边界。 |

| C++ 网络 | TCP、粘包/半包、字节序、协议边界、Asio strand 达到“能设计”。 | 有协议测试与一次异常链路复盘。 |
| SQL：SQLite + MySQL | 表设计、索引、事务、预编译语句、连接池/错误边界达到“能用”。 | W9 SQLite 测试实现、W11 MySQL 集成实现与同业务测试。 |
| Redis | 数据结构、TTL、限流、JWT 撤销的取舍达到“能用”。 | W12 登录限流和一个受控的 Token 撤销流程。 |
| 工程化 | Git、CMake target、CTest、调试器、日志、README 达到“能用”。 | 新环境复现、清晰小提交、自动测试命令。 |
| Linux / OS | 文件/进程/权限/网络命令、线程进程与 TCP 基础达到“能讲”。 | 能在 Linux 或 WSL 构建一个小 C++ 程序，并回答常见 OS 网络问题。 |
| 算法 | 数组链表、栈队列、哈希、二叉树、二分、双指针、滑窗、DFS/BFS、简单 DP 达到“能写”。 | 80–120 道高频题按错题复盘，不追求无效刷题量。 |

### 只需了解，不作为主线

- QML：完成一个 1–2 天的最小界面实验，能说明它与 Widgets 的适用场景；
- Node/Express：作为 Auth 服务的辅助能力，负责账户、JWT 与 Redis 限流；
- Docker Compose、GitHub Actions：作为 ChatHub 的交付能力；
- Protobuf/gRPC、协程：只在主线完成后根据明确岗位要求做小 spike。

## 8. 可投递的作品集与简历证据

春招前至少具备：

1. **ChatHub**：公开仓库、README、架构图、协议/API 文档、Compose、测试命令、CI 状态与演示视频；能讲 3 个真实问题（如粘包、回执归属、同名登录顶替）以及如何验证修复。
2. **数据库与安全证据**：能解释 SQLite/MySQL 的职责差异、索引/事务取舍、Redis 限流 TTL 与 JWT 撤销边界。
3. **过程证据**：规范 Git 历史、需求文档、测试输出、故障复盘；不把 AI 生成代码直接当作能力证明。
4. **产品闭环与第二项目**：ChatHub 在 W13 后先完成 W14 的联系人/好友闭环；仅在 W14 也验收后，再启动 DeviceScope Lite，用于补 Qt 线程/设备通信维度。
5. **简历材料**：一页中文简历、Qt/桌面客户端版和通用 C++ 版各一份；项目都有 90 秒和 5 分钟两种讲法。

投递表至少记录：公司/岗位链接、方向、JD 关键词、投递日期、简历版本、流程状态、面试问题、缺口和下一次动作。每周只根据真实反馈调整一到两个能力缺口，避免同时换方向。

## 9. 复盘与调整规则

- 连续 30 份针对性投递无面试：优先审简历、项目可见证据、岗位匹配与投递渠道，不盲目增加新技术；
- 有笔试/面试但技术轮不过：从题目反推基础短板，形成一周专项训练；
- 进入实习：把真实工作中的需求、测试、Bug、协作方式记录为春招故事；
- 每四周做一次路线复盘：保留能提高作品和面试通过率的任务，删除只增加“技术名词”的任务。
